kb_catalog: tier-one listing and a page-count gate for choosing load vs pack

**Behaviour change to `kb_load`.** A second ceiling now applies by default: `maxRecords`, 40, held against the whole records a load hands back (superseded ones arrive as stubs and are not counted). A base of 41 or more such records that loaded on 0.1.7 now refuses, with a `message` naming the gate and the next calls. This is deliberate — the token budget cannot see shape, and a base of many short records fits it while still reading as a skim — but it is a change in what an unchanged call returns, on a patch release. To restore the old behaviour on a call-by-call basis, pass a higher `maxRecords`, or `all: true` to bypass both ceilings; a `type` filter often brings the base under the gate on its own. The intended path past the gate is the new `kb_catalog`, then `kb_pack`.

`kb_catalog` (CLI `catalog [type]`) lists every record in one line — concept id, type, title, standing, stale flag — sorted by type then title, at roughly thirty tokens each. It never refuses: it is the rung the other read tools send you to.

`kb_load`'s success branch now also reports `pageCount` and `maxRecords`, symmetric with the refusal. CLI flags that take a value accept `--flag=value` as well as `--flag value`, and a flag given no value is now an error instead of a silent fall back to the default.
